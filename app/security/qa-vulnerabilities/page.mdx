# Amaliy Xavfsizlik Sinovlari: SQLi, XSS va IDOR

Ushbu qo'llanmada QA amaliyotida eng ko'p uchraydigan uchta xavfli zaiflik va ularni tekshirish metodikasi ko'rsatiladi.

---

## 1. SQL Injection (SQLi)

### Mohiyati:
Foydalanuvchi kiritish maydoniga (input field) maxsus SQL belgilarini kiritib, serverning ma'lumotlar bazasi bilan aloqa qiluvchi so'rovini o'zgartirib yuborishi.

```sql
-- Dasturchi yozgan himoyalanmagan so'rov:
SELECT * FROM users WHERE username = 'USER_INPUT' AND password = 'PASSWORD_INPUT';

-- Agar tajovuzkor username maydoniga quyidagicha kiritsa:
admin' --

-- Serverda hosil bo'ladigan yakuniy so'rov:
SELECT * FROM users WHERE username = 'admin' --' AND password = '...';
-- (Izoh: '--' belgisi qolgan shartlarni, jumladan parolni ham e'tiborsiz qoldiradi!)
```

### QA qanday sinaydi?
1. Qidiruv, login, filtr maydonlariga quyidagi belgilarni kiritib ko'ring:
   * `'` (bitta tirnoq)
   * `"` (qo'sh tirnoq)
   * `' OR '1'='1`
   * `' OR 1=1 --`
2. **Kutilgan to'g'ri natija:** Tizim bu belgilarni oddiy matn deb qabul qilishi va *"Foydalanuvchi topilmadi"* yoki xavfsiz xabar qaytarishi kerak.
3. **Xavfli belgi:** Tizim qulab tushib, `SQL syntax error` yoki `PostgreSQL / MySQL error` kabi ichki xatoliklarni ekranga chiqarsa, demak tizim zaif!

---

## 2. Cross-Site Scripting (XSS)

### Mohiyati:
Foydalanuvchi kiritgan zararli JavaScript kodi boshqa foydalanuvchilarning brauzerida bajarilib ketishi. Natijada boshqa odamning `Cookie` sessiyasi (Session Hijacking) o'g'irlanishi mumkin.

### QA qanday sinaydi?
Izoh qoldirish (comment), profil nomi (username), mahsulot ta'rifi kabi maydonlarga quyidagi skriptlarni kiritib saqlang:
```html
<script>alert('XSS zaifligi topildi!')</script>
<img src="x" onerror="alert('XSS!')" />
```
* **Agar sahifani yangilaganda brauzerda modal xabarnoma (`alert`) chiqsa:** Demak, ilova matnni tozalab (sanitize / HTML escape) saqlamayapti va jiddiy XSS zaifligi mavjud.
* **To'g'ri natija:** Brauzer ushbu matnni shunchaki harf sifatida ko'rsatishi (`&lt;script&gt;...&lt;/script&gt;`) kerak, uni kod sifatida bajarmasligi lozim.

---

## 3. IDOR (Insecure Direct Object Reference)

### Mohiyati:
API da obyekt identifikatoriga (ID) to'g'ridan-to'g'ri murojaat qilinganda, foydalanuvchining unga ruxsati bor-yo'qligi tekshirilmasligi.

```
Foydalanuvchi A (Oddiy mijoz)
        │
        ├──────► GET /api/v1/invoices/10042  (O'zining to'lov cheki) ──► [200 OK]
        │
        └──────► GET /api/v1/invoices/10043  (Begona mijoz cheki)   ──► [200 OK] ❌ (IDOR!)
                                                                        [403 Forbidden] ✅
```

### QA qanday sinaydi (2 ta hisob usuli):
1. Ikkita alohida akkaunt oching: **Foydalanuvchi A** va **Foydalanuvchi B**.
2. Foydalanuvchi A profilida bitta hujjat (yoki buyurtma) yarating va uning ID raqamini (masalan, `845`) ko'rib oling.
3. Foydalanuvchi B akkauntiga kiring va uning brauzerida yoki Postmanda Foydalanuvchi A ga tegishli `ID: 845` ni ochishga yoki o'chirishga harakat qilib ko'ring (`GET /api/orders/845`, `DELETE /api/orders/845`).
4. **To'g'ri natija:** Tizim `403 Forbidden` yoki `404 Not Found` qaytarishi shart. Agar ma'lumot ochilsa yoki o'chirilsa — bu kritik darajadagi xatolikdir.

---

## 4. Rate Limiting va Brute Force himoyasi

Login yoki SMS-kod (OTP) tasdiqlash oynasiga parolni cheksiz marta kiritish imkoniyati bo'lmasligi kerak.

**QA tekshiruvi:**
1. Postman orqali SMS tasdiqlash so'rovini ketma-ket 10-20 marta noto'g'ri kod bilan yuboring;
2. Tizim 3 yoki 5-urinishdan so'ng so'rovlarni bloklashi (`429 Too Many Requests`) va foydalanuvchini 5 daqiqaga to'xtatib turishi shart.
