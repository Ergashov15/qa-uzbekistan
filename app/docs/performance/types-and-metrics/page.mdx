# Yuklama Turlari va Samaradorlik Metrikalari

Samaradorlik sinovi faqat bitta kompyuterdan millionta so'rov yuborish emas. U aniq maqsadga yo'naltirilgan bir necha xil sinov turlaridan va to'g'ri o'lchov ko'rsatkichlaridan iborat.

---

## 1. Samaradorlik sinovining asosiy turlari

```
Yuklama (Foydalanuvchilar)
   ▲
   │        ┌───────────────┐
   │        │ STRESS TEST   │ ◄─── Tizimning sinish nuqtasi (Breakpoint)
   │        └───────────────┘
   │
   │   ┌──┐               ┌──┐
   │   │  │ SPIKE TEST    │  │ ◄─── Qisqa muddatli keskin sakrash
   │   │  │               │  │
   │ ┌─┴──┴───────────────┴──┴─┐
   │ │       LOAD TEST         │ ◄─── Odatdagi rejalashtirilgan eng yuqori yuklama
   │ └─────────────────────────┘
   │ ═════════════════════════════ SOAK TEST (24-72 soat bir xil yuklama)
   └────────────────────────────────────────────────────────► Vaqt
```

### 1.1. Load Testing (Yuklama sinovi)
* **Maqsad:** Tizim oldindan kutilgan odatiy va eng yuqori (peak) foydalanuvchilar oqimini ko'tara olishini tekshirish.
* **Misol:** Elektron do'konda odatda kechki soat 20:00 da 5,000 foydalanuvchi xarid qiladi. Biz 5,000 virtual foydalanuvchi bilan tizimning tezligini o'lchaymiz.

### 1.2. Stress Testing (Zo'riqish sinovi)
* **Maqsad:** Tizimning sinish nuqtasini (**Breakpoint**) aniqlash. Tizim qachon javob bermay qoladi va eng muhimi — yuklama pasayganda u o'zini o'zi qayta tiklay oladimi (Graceful Recovery)?
* **Misol:** 5,000 foydalanuvchidan boshlab har 2 daqiqada 1,000 tadan qo'shib boramiz: 6,000 → 8,000 → 12,000... Server qaysi nuqtada `500` yoki `504 Gateway Timeout` berishini aniqlaymiz.

### 1.3. Spike Testing (Keskin sakrash sinovi)
* **Maqsad:** Foydalanuvchilar soni soniyalar ichida keskin oshib ketganda (masalan, mashhur bloger reklama berganda yoki to'lov chegirmasi e'lon qilinganda) tizimning xatti-harakatini ko'rish.
* **Misol:** 10 soniya ichida yuklama 100 tadan 10,000 tagacha ko'tariladi va 1 daqiqadan so'ng yana tushadi.

### 1.4. Soak / Endurance Testing (Chidamlilik sinovi)
* **Maqsad:** O'rtacha yuklamani uzoq vaqt (12 soatdan 72 soatgacha) uzluksiz ushlab turish.
* **Nimani topadi:** Vaqt o'tishi bilan yuzaga keladigan **Memory Leak** (xotira tozalab yuborilmasligi) va ma'lumotlar bazasi ulanishlarining tugab qolishi (Connection pool exhaustion).

## 2. Muhim samaradorlik metrikalari

Ko'pincha yangi boshlovchilar *"O'rtacha javob berish vaqti 200 ms chiqdi, demak tizim a'lo ishlayapti"* deb xato xulosa qilishadi. Real dunyoda o'rtacha qiymat aldamchidir.

| Metrika | Ta'rif | Sanoat standarti |
| :--- | :--- | :--- |
| **Response Time** | Mijoz so'rov yuborganidan to javobning oxirgi baytini qabul qilib olguncha o'tgan umumiy vaqt. | Ideal holda &lt; 200-500 ms |
| **Latency** | So'rovning serverga yetib borishi va server qayta ishlashni boshlagunga qadar bo'lgan tarmoq kechikishi. | &lt; 50-100 ms |
| **Throughput (RPS)** | Server bir soniyada qayta ishlay oladigan so'rovlar soni (Requests Per Second). | Loyiha talabiga ko'ra |
| **Error Rate** | Umumiy so'rovlar ichida xato bilan (`4xx`, `5xx`) tugagan so'rovlar foizi. | Ideal holda &lt; 0.1% |

### Nega Persentillar (p90, p95, p99) o'rtacha qiymatdan (Average) muhimroq?

Agar 100 ta foydalanuvchidan 95 tasiga sayt **100 ms** da ochilsa, lekin 5 ta foydalanuvchiga **10 soniya**da (10,000 ms) ochilsa:
* **O'rtacha (Average):** `(95*100 + 5*10000) / 100 = 595 ms`. Tashqaridan qaraganda yarim soniya normal ko'rinadi.
* **p95 (95-persentil):** 100 ms (Foydalanuvchilarning 95 foizi tizimni tez deb hisoblaydi).
* **p99 (99-persentil):** 10,000 ms (Eng muhim va eng ko'p xarid qiladigan 5% auditoriya 10 soniya kutmoqda!).

<Callout type="info">
  **Sanoat qoidasi:** Yirik kompaniyalar (Google, Netflix, Stripe) o'z xizmatlari sifatini o'rtacha qiymat bilan emas, aynan **p95** va **p99** persentillari bilan baholaydilar.
</Callout>
